# NegativeViewer 现役开发计划

版本：v1  
日期：2026-08-13  
当前基线：`v1.1.0`  
目标版本：`v1.2.0`

## 1. 文档定位

本文是 NegativeViewer 后续开发的现役计划，主要目标是恢复高分辨率静态拍照保存，并建立可持续验证的图像处理链路。

- `README.md` 继续作为现役功能、使用方法和构建说明的权威入口。
- 本文负责开发优先级、技术路线和验收标准。
- `PLAN.md` 与 `PLAN2.md` 保留为早期设计记录，不作为当前实现和开发顺序的依据。
- 实际行为与本文不一致时，以当前代码和真机验证结果为准，并及时更新本文。

## 2. 当前基线

`v1.1.0` 已实现：

- CameraX 后置相机实时取景。
- OpenGL ES shader 实时处理。
- `NORMAL`、`COLOR`、`B&W`、`COLOR+`、`ALL` 五种模式。
- Exposure、Brightness、Contrast、Gamma 和 RGB gain 调节。
- COLOR+ 片基采样、重新采样和重置。
- 点击对焦、长按保持对焦/测光区域、双指缩放。
- 单图、原始预览帧与处理预览帧拼接保存。
- MediaStore 保存至 `Pictures/NegativeViewer/`。

当前主要问题：

- 快门保存的是 OpenGL 预览纹理，不是 CameraX 高分辨率静态照片。
- GLSL 与 Kotlin 分别实现图像处理公式，缺少自动化一致性验证。
- 项目没有自动化测试，主要依赖编译和 Android 真机验收。
- 拍摄、处理和保存过程的用户反馈不足。
- “相机曝光”和后处理 `Exposure` 的产品语义尚未明确区分。

## 3. v1.2.0 目标

### 3.1 核心目标

建立以下高分辨率保存链路：

```text
用户按下快门
  -> 冻结当前模式、处理参数和片基样本
  -> CameraX ImageCapture 拍摄高分辨率 JPEG
  -> 读取并校正 EXIF 方向
  -> 使用冻结参数进行静态图片处理
  -> 根据保存模式生成单图、拼接图或四宫格
  -> MediaStore 保存
  -> 返回保存结果或可行动的错误信息
```

### 3.2 用户价值

- 保存结果使用相机静态拍照分辨率，不再受预览纹理尺寸限制。
- 成片使用按下快门时看到的模式和参数，不受处理期间 UI 操作影响。
- 预览和成片处理顺序一致，颜色差异可被测试和控制。
- 用户能明确知道当前处于拍摄、处理、保存成功或失败状态。

### 3.3 非目标

以下功能不进入 `v1.2.0`：

- 图片导入。
- 自动边框检测。
- 手动裁切和透视校正。
- RAW/DNG 保存。
- 批量处理。
- 云端处理或账号系统。

## 4. 核心技术决策

### 4.1 高分辨率照片作为正式输出

- CameraX `ImageCapture` JPEG 是正式成片输入。
- OpenGL 预览继续用于实时取景和效果反馈。
- 当前预览帧保存能力暂时保留，作为调试工具或高分辨率链路失败时的可选回退；不得静默回退。
- 如果发生回退，UI 必须明确告知用户保存的是预览分辨率图片。

### 4.2 快门参数快照

按下快门时创建不可变的拍摄快照，至少包含：

```kotlin
data class CaptureProcessingSnapshot(
    val previewMode: PreviewMode,
    val saveOutputMode: SaveOutputMode,
    val processingParams: ProcessingParams,
    val orangeMaskSample: OrangeMaskSample?,
)
```

后续处理只读取该快照，不再读取实时 `CameraUiState`，避免处理期间用户调节参数导致预览与成片错位。

### 4.3 统一处理顺序

GLSL 和 Kotlin 静态处理必须采用同一语义顺序：

1. 读取输入颜色。
2. COLOR+ 可选片基归一化。
3. COLOR 模式执行彩色反相；B&W 模式执行灰度化后反相。
4. 彩色反相模式应用 RGB gain。
5. 应用 Exposure。
6. 应用 Contrast。
7. 应用 Brightness。
8. 应用 Gamma。
9. 将结果限制到合法颜色范围。

两套实现不要求浮点结果逐位相同，但必须通过固定测试图片和误差阈值验证视觉一致性。

### 4.4 内存优先

- 不在内存中无必要地同时持有原图、多个处理副本和拼接结果。
- Bitmap 的所有权和回收责任必须清晰，异常路径也必须释放资源。
- 在目标真机上记录高分辨率处理时的峰值内存和耗时。
- 低内存时应明确失败或按显式策略降采样，不得崩溃或静默输出损坏图片。

## 5. 分阶段实施计划

### 阶段 A：建立测试基线

目标：在重接拍照链路前固定现有状态和处理语义。

任务：

- 增加 `CameraViewModel` 状态测试。
- 增加 `NegativeBitmapProcessor` 小尺寸像素测试。
- 为 COLOR、B&W、COLOR+ 和 ALL 准备固定输入及期望结果。
- 测试默认值、参数边界和重置行为。
- 将自动化测试加入 GitHub Actions PR 检查。

重点测试：

- 五种预览模式循环顺序。
- `NORMAL` 与 `ALL` 强制使用单图保存模式。
- 片基采样、重新采样和重置状态。
- COLOR+ 无片基样本时退化为普通 COLOR。
- Tone 与 RGB 默认值和重置结果。
- 静态处理不会修改输入 Bitmap。

完成标准：

- 测试可在 CI 稳定运行。
- 后续算法变更造成的结果变化能够被自动检测。

### 阶段 B：建立高分辨率拍照主链路

目标：用 CameraX `ImageCapture` 替换预览帧作为正式保存输入。

任务：

- 整合现有 `ImageCaptureController` 到快门流程。
- 按下快门时创建 `CaptureProcessingSnapshot`。
- 使用缓存目录保存 CameraX 临时 JPEG。
- 使用 `ExifOrientationUtils` 校正方向。
- 使用 `NegativeBitmapProcessor` 生成静态处理结果。
- 使用 `MediaStoreImageSaver` 发布最终 JPEG。
- 确保临时文件在成功和失败路径均能正确收口。

模式行为：

| 模式 | 正式保存行为 |
|---|---|
| `NORMAL` | 保存 CameraX 原始静态照片 |
| `COLOR` | 保存高分辨率彩色反相结果 |
| `B&W` | 保存高分辨率灰度反相结果 |
| `COLOR+` | 使用快门时冻结的片基样本保存校正结果 |
| `ALL` | 由同一张高分辨率原图生成四宫格结果 |

完成标准：

- 最终图片尺寸来自 CameraX 静态照片，而不是 OpenGL 预览纹理。
- 拍摄过程中调节 UI 不会改变正在处理的照片。
- 连续完成至少 10 次拍摄，应用不崩溃且没有明显内存持续增长。

### 阶段 C：恢复高分辨率拼接保存

目标：单图链路稳定后，再接入原图与处理图拼接。

任务：

- `NORMAL` 和 `ALL` 继续强制单图输出。
- COLOR、B&W、COLOR+ 支持处理图单图或高分辨率拼接图。
- 竖图左右拼接，原图在左、处理图在右。
- 横图上下拼接，原图在上、处理图在下。
- 优化 `StitchComposer` 的缩放和内存生命周期。
- 输出文件名明确包含模式和 `STITCH`。

完成标准：

- 拼接方向、比例和图像方向正确。
- 原图与处理图来自同一次 CameraX 拍摄。
- 高像素输入下不会因同时持有过多 Bitmap 而频繁内存溢出。

### 阶段 D：预览与成片一致性

目标：控制 GLSL 预览和 Kotlin 静态处理之间的可见差异。

任务：

- 集中定义参数默认值、最小值和最大值。
- 核对 GLSL 与 Kotlin 的处理顺序和边界裁剪。
- 建立若干组参数化金标准测试。
- 记录允许的颜色误差和产生误差的原因。
- 真机比较 COLOR、B&W、COLOR+ 和 ALL 的预览与成片。

完成标准：

- 常用参数范围内没有明显的色调跳变。
- 如果设备相机管线导致预览和 JPEG 天生存在差异，README 中明确说明该限制。

### 阶段 E：拍摄反馈与错误恢复

目标：让用户始终知道系统正在做什么，以及失败后如何行动。

建议状态：

```kotlin
enum class CaptureStage {
    IDLE,
    CAPTURING,
    PROCESSING,
    SAVING,
}
```

任务：

- 分开展示拍摄、处理和保存状态。
- 处理中禁用重复快门，避免堆积多个高内存任务。
- 保存成功后显示缩略图、图片尺寸和保存位置。
- 权限、相机、处理、内存和 MediaStore 错误使用不同提示。
- 错误提示给出明确下一步，例如重试、降低输出尺寸或检查存储空间。
- 将后处理 `Exposure` 与未来的相机 `Camera EV` 明确区分。

完成标准：

- 所有失败路径都能恢复到可再次拍摄状态。
- 用户不会把处理中误判为应用卡死。
- 应用不会静默回退到低分辨率保存。

## 6. 预计代码影响面

主要修改：

- `state/CameraUiState.kt`：增加拍摄阶段和结果信息。
- `state/CameraViewModel.kt`：管理快门参数快照及状态转换。
- `state/PreviewMode.kt`：增加快照模型或相关输出模型。
- `ui/CameraScreen.kt`：重接快门流程和状态反馈。
- `camera/ImageCaptureController.kt`：正式接入 CameraX 静态拍照。
- `processing/NegativeBitmapProcessor.kt`：统一处理语义并控制内存。
- `processing/StitchComposer.kt`：支持高分辨率拼接和资源收口。
- `storage/MediaStoreImageSaver.kt`：完善命名和保存结果模型。
- `.github/workflows/android-pr-check.yml`：运行自动化测试。

可能新增：

- `state/CaptureProcessingSnapshot.kt`
- `state/CaptureStage.kt`
- `app/src/test/` 下的 ViewModel 和图像处理测试
- 小尺寸测试图片与金标准数据

## 7. 验证计划

### 7.1 自动化检查

- Kotlin 单元测试。
- ViewModel 状态转换测试。
- 小尺寸 Bitmap 处理测试。
- debug 编译。
- release 编译。
- GitHub Actions workflow YAML 解析和实际运行。

### 7.2 Android 真机验收

至少覆盖：

- 首次授权、拒绝后重试和从设置恢复权限。
- 五种模式预览与保存。
- COLOR+ 未采样、已采样、重新采样和重置。
- Tone/RGB 极值和默认值。
- 点击对焦、长按对焦、曝光拖动和缩放。
- 竖拍、横向握持产生的 EXIF 方向变化。
- 单图、拼接图和 ALL 四宫格。
- 连续 10 次拍摄。
- 应用前后台切换后继续拍摄。
- 存储失败或低内存情况下的恢复。

### 7.3 质量记录

每个候选发布版本至少记录：

- 输入 JPEG 尺寸。
- 输出 JPEG 尺寸。
- 从按下快门到保存完成的耗时。
- 处理期间峰值内存。
- 测试设备型号和 Android 版本。
- 已知的预览与成片差异。

## 8. v1.2.0 发布门槛

只有同时满足以下条件才进入发布：

- 高分辨率单图保存通过真机验收。
- 高分辨率拼接和 ALL 保存通过真机验收。
- COLOR、B&W、COLOR+ 的主要参数与预览没有明显跳变。
- 自动化测试、debug 编译和 release 编译通过。
- 连续拍摄没有可复现的崩溃或资源泄漏。
- README 已同步实际保存行为、限制和安装方式。
- GitHub Release 附件由用户在目标 Android 设备上安装验收。

## 9. 后续版本候选

完成 `v1.2.0` 后，建议按以下顺序推进：

1. `v1.3.0`：参数预设、最近参数持久化和拍摄历史缩略图。
2. `v1.4.0`：手动裁切和四点透视校正。
3. `v1.5.0`：导入已有底片照片并复用同一处理链路。
4. 后续版本：自动边框检测、批量处理和 RAW/DNG 可行性验证。

自动裁切、导入和 RAW 工作流不得早于高分辨率主链路、内存控制和自动化测试稳定完成。

## 10. 推荐执行顺序

```text
阶段 A：测试基线
  -> 阶段 B：高分辨率单图
  -> 阶段 C：高分辨率拼接
  -> 阶段 D：预览与成片一致性
  -> 阶段 E：交互和错误恢复
  -> Android 真机验收
  -> README 与发布说明同步
  -> v1.2.0 候选发布
```

每个阶段只处理本阶段目标；编译或测试失败时先修复当前问题，不继续叠加下一阶段功能。
